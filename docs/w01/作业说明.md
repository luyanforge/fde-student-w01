## 二、关键判断及依据

**1. 把"复购下滑"拆成三层，只承诺能验证的那一层**

- 业务结果层（为什么下滑）：归因未验证、无基线数值、无口径，本期无法回答。
- 工作过程层（谁在什么时点挑名单、怎么用建议）：产品能嵌入的位置，本期唯一可验证的层次。
- 能力供给层（标准产品能否在客户语义下产出可用名单）：fit-gap 回答的问题。

**2. 发起人判断不能当项目前提**

客户说"会员老化比较明显"。追问后他本人承认："会员老化是我的判断，数据能不能支持，也还要核实。"因此该归因记为待验证假设，不作为项目依据。同理，"连续四个季度下滑"虽有此结论，但报表出处与具体数值始终未取得。

**3. 通过沟通把承诺边界谈成了文字共识**

三个拍板点中，首期范围与验收口径客户选择了建议的 A 方案，并三次（`MSG-00832`、`MSG-00838`、`MSG-00844`）表述一致：**三个月是个人期望，不是期限，也不是验收标准**。这一条写进了范围确认备忘并请对方回"确认"，避免口头共识后续漂移。

首期范围明确砍掉标签执行：客户连接器要到 W8 才做，现在答应等于承诺一个还做不出来的东西。

**4. 未知如实保留**

沈总能提供目标、边界、决策和资源，但不掌握数据与流程细节——他给的四位联系人与材料包里的分工逐字一致，一个也没多。因此流程与数据类诉求在 W1 最多到 `reported`/`unknown`。这是角色可及性的限制，不是取证不力，报告里单列一节说明。

## 三、过程中修的一个产品缺陷

首次真模型验证时 8 项通过，`http_action`、`idempotency`、`undo`、`reject_change` 4 项全部失败，报错均为 `MODEL_HTTP_400`。

根因是产品自身的工具 schema 有缺陷：`prepare_tag` 的参数 `tag` 只写了 `{"enum": [...]}`，没有声明 `type`。Moonshot 端点严格校验 JSON Schema，直接拒绝（`properties.tag: type is not defined`）。补上 `type: "string"` 后同一请求返回 200。

修法压在适配器层：`platform/fde_product/models.py` 新增 `normalized_tools()`，按 enum 取值推断缺失的 type；工具契约、名称、必填项与业务语义均未改动，`agent.py` 业务代码零改动。依据是任务书"不同模型的接口不兼容时修改适配器并保留证据"，400→200 的原始对照已写入报告第九节。

另外两处环境处理也留下了脚本：`uuid_utils` 的原生扩展被本机应用程序控制策略拦截，在两个调用点加了纯 Python 回退；`promptfooconfig.yaml` 的解释器路径改为本机 Windows 路径（原文件保留为 `.orig`）。

## 四、仓库的使用方式

仓库按"先干净、后改后"组织成四个提交：

| 提交 | 内容 |
|---|---|
| `543dd9b` | 标准产品 `0.2.0-w1` 原始基线，未修改 |
| `e73e60c` | 适配器修复 + W01 全部交付物 |
| `38e04ce` | README 重写为工程记录 + PR 模板 |
| `8c5e230` | 工具脚本去掉本机路径，改为自动定位 Node |

基线做了**字节级**校验：按 `MANIFEST.json` 逐文件比对 Git 内部 blob 的 SHA-256，46/46 一致，0 不匹配、0 缺失。`git diff 543dd9b HEAD -- platform/ evals/` 即可看到全部业务代码改动（2 个文件）。

仓库根目录的 `.gitattributes`（内容 `* -text`）只用于关闭行尾自动转换——本机 `core.autocrlf=true` 会把 `sample_data/` 下 4 个 CRLF 换行的 CSV 改写成 LF，那样基线就不再是"原样"。

`.venv`、`.runtime`、`.model.env`、`*.key` 均未入库，也已列入 `.gitignore`。模型密钥通过 `FDE_MODEL_KEY_FILE` 从本地文件读入，不进代码、不进命令行。
