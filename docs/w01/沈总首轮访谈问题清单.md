> 用途：为 `fit-gap` 初步版与立项四问补第一手依据，形成"继续 / 带条件继续 / 暂缓"的判断

## 一、本周作业要求（先明确清单为谁服务）

| 项目 | 内容 |
| --- | --- |
| 本周任务 | 接手标准产品 `0.2.0-w1`，运行验证后判断**是否进入下一阶段**，而不是提前承诺功能或效果 |
| 必交产出 | 四份 JSON（`environment_check` / `product_fit_gap` / `model_baseline` / `runtime_evidence`）+ `docs/w01/project_assessment.md` 立项报告 |
| 访谈约束 | **W1 只开放沈总**；每周每角色最多 2 次正式访谈（预扣，系统失败返还，主动结束不返还） |
| 证据要求 | 分类（产品已有/客户配置/系统适配/产品缺口/暂不承诺/待判断）与证据状态（`verified`/`reported`/`unknown`/`conflicting`）**分别填写**；沈总单方说法只能是 `reported`，不能记 `verified` |
| 报告要点 | 区分诉求与事实、提出必要核查对象、在不确定性中守住承诺边界 |

**由此推导出本次访谈的三个硬要求：**

1. **只有 2 次机会 → 清单必须分优先级**，第一次拿"业务问题 + 验收标准 + 协作路径"，技术细节留给老周，不要浪费在沈总回答不了的问题上。
2. **沈总的每句话默认是 `reported`** → 提问时就要顺手拿到"这个数字/判断在哪份材料里"，为 `locator` 字段留出可定位的出处。
3. **W1 其他角色不可访谈** → 沈总是唯一的"通道"，问题必须包含"下一步找谁、拿什么材料、谁来安排"。

## 四、问题清单（含提问意图与追问）

> 记号说明：**【主问】** 必问；**【追问】** 视回答展开；`→` 表示提问意图。

### A. 开场与共识（3 分钟，2 问）

**A1【主问】** 我先把从您邮件里读到的理解复述一遍：您希望在三个月内用我们的标准产品改善会员复购，先解决"识别哪些会员需要重点经营"，并且直接把运营建议给到小林，而不是再让她多整理一套表。哪一句跟您的原意不一样？

> → 校准理解，避免带着自己的假设往下问。**他纠正的那一句，往往就是最在意的点**；纠正内容本身就是高价值信息。

**A2【主问】** 这次交流我会做记录，报告里引用您的原话时会标明"沈总转述、待核实"，不会写成已经核实的业务事实。有没有哪些内容不方便写进书面材料？

> → 开场就立证据边界，既是合规，也让后面标 `reported` 有据可依。同时观察他对"待核实"这个说法的反应——在意的人通常会主动补充依据。

### B. 业务问题：复购下滑到底是件什么事（8 分钟）

**B1【主问】** 复购率连续四个季度下滑——这个结论您是在哪份报表或哪次会上看到的？最近一次看到的四个季度数值大概是多少？

> → 把形容词换成可定位的数字。这是全篇的基线：**没有基线，三个月的"见效"就无法验收**。答不出具体数值也很正常，但要拿到"哪份报表、谁出的"。

**B2【主问】** 咱们内部对"复购率"的定义是什么？按季度还是按月算、算哪些渠道——400 家门店、线上商城、小程序是一起算还是分开算？

> → 指标口径是 fit-gap 里最典型的"客户配置"项。口径不定，"复购率改善"这句话就无法写进验收。

**B3【追问】** 下滑是全面的，还是某些区域、品类、会员层级更明显？之前有没有做过分层看？

> → 检验问题是否已经被拆解过。若从未分层，说明客户连"问题在哪"都还没定位，产品再准也只是给一个更快的错误答案。

**B4【主问】** 除了复购率，还有哪个指标一动，您会觉得这件事成了？

> → 业务方嘴上说复购率，真正在意的常是响应率、券核销率、运营人效或"能向董事会讲清楚的过程"。找到真实成功信号，报告的验收段才写得实。

### C. 挑战归因："会员老化"是判断还是结论（6 分钟）

**C1【主问】** 您提到会员老化比较明显——这个判断是从哪份数据或哪次讨论来的？方便的话我想看一下原始的那份分析。

> → 把归因落到证据。拿不出就明确记 `reported`，并在报告里保留为**待验证假设**，不能写成项目前提。这是本周最容易踩的坑：把发起人的判断当成已核实事实。

**C2【追问】** 如果老化不是主因，您觉得第二可能的原因是什么？价格、竞品、门店覆盖变化、还是消费往线上迁移？

> → 防止项目一开始就把方案锁死在单一假设上；也提前为"数据反驳假设"留出台阶，后面拿数据说话时不至于变成否定领导。

**C3【主问】** 上一个智能营销项目，当时立项的判断是什么？后来发现哪一步判断错了——是需求没定清、数据不够、门店没执行，还是效果没法衡量？

> → 失败项目的复盘是全场性价比最高的信息。他说"供应商没交付好"，但**"没交付好"具体指哪一环**决定了这次要防什么。这题答得越具体，本周风险清单越靠谱。

### D. 当前工作方式：一次具体的运营动作（8 分钟）

**D1【主问】** 现在要定"这个月重点经营哪些会员"，是小林在做吗？她最近一次做这件事大概是怎样的——从打开哪张表开始，到最后交出什么？

> → 案例手册给的方法：**问"最近一次具体怎样做"，不问"流程是怎样的"**。流程描述会美化，具体事例会暴露真实工具和真实耗时。

**D2【主问】** 从"决定要经营谁"到"会员真的被触达到"，中间要经过哪些人、哪些系统？哪一步最容易卡住或者返工？

> → 定位真正瓶颈。如果卡点在门店执行或触达工具，而不在识别，那么"更准的名单"价值有限，产品定位要改——这一条会直接影响第四问的结论。

**D3【追问】** 这套动作一个月做几次？一次大概占小林多少时间？

> → 量化改善空间，为"值不值得做"提供基线。也是判断投入产出是否合理的最朴素依据。

**D4【主问】** 您提到 80 万活跃会员——这个数是从哪个系统取的？"活跃"是怎么算的，多久内有消费，还是有互动就算？

> → 区分"客户声称的规模"和"真正可用的数据范围"。80 万若无法定位来源，报告里必须标 `unknown`，不能拿它做容量或成本推算。

### E. 输出与去向：结果交给谁、落到哪里（7 分钟）

**E1【主问】** 您说"直接给小林一些运营建议"——您希望她拿到的是什么：一份名单、每个人的下降情况和建议理由，还是可以直接点一下就执行的动作？

> → 界定输出形态。这一问的答案直接决定 fit-gap 的分类：只出名单和建议 → 大概率"产品已有"；要写回客户系统 → "系统适配"或"待判断"。

**E2【追问】** 建议给出去之后，小林是照着做，还是会自己再判断一遍？她凭什么判断这条建议靠不靠谱？

> → 确认人工确认点的位置，也确定结果质量由谁检验。这是"能不能承诺效果"的分水岭。

**E3【主问】** 这些会员最终要在哪个系统里被标记或打标签？是咱们的会员系统、CRM，还是门店自己维护的表？

> → 写操作是范围最大的一块。产品当前只有**样例标签 API**，青禾的连接器要到 W8 才做，所以这题问清目标系统，本周才能在 fit-gap 里如实标"系统适配/待判断"，而不是含糊承诺。

**E4【追问】** 门店侧陈姐那边在这件事里做什么？会员到店之后需要店长或店员配合吗？

> → 确认门店是否为执行链一环。W1 不能访谈陈姐，这里只能拿到沈总的**转述**，报告里必须写成 `reported` 并列出待核实项。

### F. 验收与时间压力（6 分钟）

**F1【主问】** 三个月看到效果——三个月后您拿什么向董事会汇报？是复购率真的变了，还是"这套流程跑通了、能看到数据"？

> → 区分"业务效果承诺"和"能力验证"。W1 只能承诺可验证的范围，这题决定报告里的承诺边界写在哪。

**F2【追问】** 如果三个月复购率没有明显变化，但运营动作确实跑起来了、名单也确实被用上了，这算成功还是失败？

> → 逼出真实验收底线。客户往往两个都想要，必须让他排序——**否则后面出事时，"没效果"会被追溯成供应商责任**。

**F3【追问】** 董事会和上级对这个项目的期待，是"必须上"，还是"做不成可以停"？

> → 判断项目的政治约束强度。这直接影响第四问建议的措辞：能停就写"带条件继续"，不能停就要把条件和风险写得更硬。

### G. 数据与系统条件：只问路径，不问细节（5 分钟）

**G1【主问】** 会员、订单、门店、标签这几类数据，现在分别在哪几个系统里？有没有能直接导出的？

> → 掌握数据来源全貌。他答不上来很正常——**重点不是让他答，而是拿到"这几个系统分别归谁管"**。

**G2【主问】** 如果先做一次小范围验证，能不能给我们一批脱敏的历史数据？需要走什么审批？

> → W1 的核心交付之一是"能先验证哪一部分"。数据可得性是这条建议成立的前置条件，问不出就只能是条件句。

**G3【追问】** 数据这块我详细问老周，您帮他打个招呼，还是我自己约？他那边有什么我们需要注意的边界？

> → 明确协作授权路径，同时试探老周的实际配合度与影响力——这决定第三问里"协作条件"是标 `reported` 还是 `unknown`。

### H. 决策、预算与组织（5 分钟）

**H1【主问】** 这次的预算和合同，是已经批了额度，还是需要王经理那边走流程？大概什么节奏？

> → 材料明确说"未提供已批准预算"。要确认这是真没有、还是他没说——两者在报告里的写法完全不同。

**H2【追问】** 上一个项目的决策链和这次一样吗？当时是谁拍板继续或停掉的？

> → 识别真正的决策人。**别把沈总的态度当成组织决策**，这是立项报告最常见的判断偏差。

**H3【追问】** 除了小林，还有谁的日常工作会因为这件事发生变化？

> → 找出隐性干系人和阻力点（比如运营团队担心被替代、IT 担心增加维护）。风险清单里这些比技术风险更容易让项目停摆。

### I. 边界：明确不做的事（4 分钟）

**I1【主问】** 有哪些事是这个项目明确不能做的？比如自动发券、直接改会员等级、自动对外触达会员。

> → 从客户口中拿到"不做"清单，这是"暂不承诺"分类最硬的依据，比我们自己推测边界可靠得多。

**I2【追问】** 会员数据的使用有没有合规或内部规定上的限制？比如能不能出店、能不能给外部系统调用。

> → 提前识别阻塞项。这类限制一旦在 W4 才发现，前面所有验证都要重做。

### J. 收尾与下一步（5 分钟）

**J1【主问】** 按您刚才说的，我理解优先级是 X 最急、Y 次之、Z 可以往后放，对吗？哪一条我排错了？

> → 复述确认形成可引用的共识，同时给他一个低成本的纠错机会。

**J2【主问】** 接下来两周，我们先验证"用你们的历史数据跑出一份下降会员名单 + 每个人的建议理由"，您看这个切口合适吗？太大还是太小？

> → 把"能先验证哪一部分"变成他当场点头的具体提议，而不是开放式讨论。

**J3【主问】** 为了这个切口，我需要三样东西：一批脱敏数据、小林一个小时的访谈、老周给一份系统与接口说明。您能帮着安排吗？我什么时候再来跟您确认一次？

> → 拿到承诺与下一次时间点。每周每角色只有 2 次访谈，**第二次必须是带着第一次的成果去**，不能重复问同样的问题。

## 五、提问顺序与节奏（建议 50 分钟）

| 段 | 内容 | 时长 | 为什么排在这里 |
| --- | --- | --- | --- |
| A | 开场与理解校准 | 3' | 先对齐，避免整场都在错误前提上推进 |
| B | 业务问题与口径 | 8' | 从事实层开始，建立基线，后面所有判断都依赖它 |
| C | 挑战归因 | 6' | 紧接着基线追问"为什么"，此时他还在具体语境里 |
| D | 当前工作方式 | 8' | 从"为什么"落到"谁在怎么做"，拿具体事例 |
| E | 输出与去向 | 7' | 有了工作现状，才能谈结果交给谁、落到哪 |
| F | 验收与时间压力 | 6' | 此时谈承诺边界最自然，不显得推诿 |
| G | 数据与系统路径 | 5' | 技术条件放在后面，避免开场就被细节带偏 |
| H | 决策与预算 | 5' | 组织与钱的事放在信任建立之后 |
| I | 明确不做的边界 | 4' | 收尾前的"减法"，比前面所有加法都值钱 |
| J | 复述与下一步 | 5' | 以具体承诺结束，不留"回头再聊" |

**顺序原则：事实 → 归因 → 工作 → 输出 → 验收 → 条件 → 决策 → 边界 → 承诺。**
越靠后的问题越敏感（预算、决策人、失败复盘），放前面容易被挡回来；但也不能放到最后才问，否则没时间追。

**可以跳过的**：B3、D3、E4、H3、I2——它们是加分项，时间不够时留给第二次访谈。
**不能跳过的**：B1、B2、C1、D1、D2、E1、F1、G2、I1、J2。

## 六、高频模糊回答与追问预案

| 客户可能说 | 不要接受的说法 | 应追问 |
| --- | --- | --- |
| "复购率一直在跌，这个你们不用管细节" | 接受"在跌"作为事实 | "大概跌了多少？这份数我能不能看到原始报表？" |
| "会员老化很明显" | 记成已验证事实 | "这个结论是哪次分析得出的？有没有分年龄或入会年份的分布？" |
| "你们是专业的，怎么做你们定" | 当成需求已明确 | "那验收的时候，是您来判断还是小林判断？她认可就算过吗？" |
| "先做起来看，效果肯定有" | 当成效果承诺 | "如果三个月复购没动，但这个流程在跑，咱们怎么定性？" |
| "数据都有，随时能给" | 记成数据可用 | "具体是哪位同事能导？导出需要走审批吗？脱敏谁来做？" |

**通用追问三连**：能举个例子吗（最近一次）→ 当时具体怎么做的 → 结果怎么判断的。

## 七、访谈后记录表（对齐材料 `04_立项四问与访谈提纲.md`）

| 记录项 | 填写要求 |
| --- | --- |
| 本次访谈目的 | 从第二节六个目的中挑本次实际覆盖的 3–4 条 |
| 优先问题与原因 | 记录实际问了哪几题、为什么临时调整顺序 |
| 客户原话与位置 | 引用邮件段落，或访谈导出记录的消息 ID（这是 `locator` 的来源） |
| 我当前的解释 | 明确写"这是我的推断"，不能与客户原话混写 |
| 已核实／角色转述／未知／存在冲突 | 逐条标 `verified` / `reported` / `unknown` / `conflicting` 并说明依据 |
| 尚不能承诺的事项 | 效果数字、自动发券、系统写回、门店执行等 |
| 下一步需要谁提供什么证据 | 具体到人 + 具体材料 + 大概时间 |

**填写纪律**：
- 不要因为沈总语气肯定，就把他的说法记成 `verified`；
- 也不要为了显得谨慎，把邮件里白纸黑字的内容都写成 `unknown`——**邮件能证明的是"他这么说过"，不是"事实如此"**，这个区别要在 `note` 里写清楚。

## 八、禁忌清单

1. **不要问功能清单式问题**（"你们需不需要 A 功能、B 功能"）——这会把访谈变成需求收集，而本周要判断的是"值不值得做"。
2. **不要引导**（"如果有个工具能自动识别，是不是很好？"）——他会顺着说"是"，这条证据就废了。
3. **不要向沈总要技术细节**（字段、接口、表结构）——他答不了，等于浪费仅有的 2 次机会。
4. **不要在访谈中承诺效果数字或工期**——承诺边界是本周的评分项之一。
5. **不要把沈总的单方判断写成业务事实**——`reported` 与 `verified` 必须分开。
6. **不要一次把清单问完**——问题随回答调整，遇到高价值线索宁可深挖一题。
